# 外部リポジトリ実証検証レポート（5 アーキタイプ）

本ドキュメントは、`ai-sdlc-maturity-model-skills`（AI-SDLC 成熟度アセスメントスキル）の判定精度、スクリプト実行安定性、およびエッジケースへの耐性を検証するために、5 つの代表的な公開 OSS リポジトリで実施した実証評価の記録です。

---

## 1. 検証設計とサンプリング根拠

### なぜ 5 リポジトリなのか（統計的根拠）
本検証の主目的は「判定基準の妥当性の確認」および「スクリプト実行エラーやエッジケースの検出（Defect Detection）」です。
定性評価・ヒューリスティック評価における統計モデル（ヤコブ・ニールセンの欠陥発見モデル：二項確率モデル）に基づきます。

$$P = 1 - (1 - p)^n$$

- **$p$（各リポジトリで特定のエッジケースや不適合に遭遇する確率）**：代表的なエッジケース（モノレポ、単独メンテナ、外部CI、AI未導入の伝統的CI等）は約 $0.30 \sim 0.35$ 程度と見積もられます。
- **$n = 5$ の場合**：
  $$P = 1 - (1 - 0.32)^5 \approx 85.5\%$$
  5 つの直交するアーキタイプを検証することで、主要なエッジケースの 85% 以上をカバーできます。
- 6 件目以降はパターンの重複が増えて限界効用が急減するため、**初期検証の費用対効果（ROI）として 5 件が最適なスイートスポット**となります。

### 検証対象の 5 アーキタイプ

「**AI活用度（高/低）** × **開発規模（チーム/ソロ）**」の $2 \times 2$ マトリクスに、構造的複雑性を持つ「**特殊系（モノレポ）**」を加えた構成です。

1. **AI先進 × 複数人チーム**: [cline/cline](https://github.com/cline/cline)
2. **AI先進 × ソロ開発**: [Wolfe-Jam/faf-cli](https://github.com/Wolfe-Jam/faf-cli)
3. **伝統的 × 大規模チーム**: [cli/cli](https://github.com/cli/cli)
4. **小規模/シンプル × 個人ライブラリ**: [sindresorhus/is](https://github.com/sindresorhus/is)
5. **特殊系（モノレポ / 多言語）**: [pnpm/pnpm](https://github.com/pnpm/pnpm)

## 3. 各検証軸での発見と知見

### 軸 1: スクリプト実行安定性
- **全件で完走**: 5 リポジトリすべてにおいて `collection_errors: []` で正常終了し、`jq`, `gh`, `git` の構文エラーや API レートリミットによる中断は発生しませんでした。
- **既定ブランチの多様性**: `cli/cli` のように既定ブランチが `trunk` の場合も、`refs/remotes/origin/HEAD` から自動検出して `is_default_branch: true` と判定されました。
- **Git LFS 依存のエッジケース（改善点）**:
  - `cline/cline` の clone 時に、環境に `git-lfs` が未導入だったため checkout が中断する現象が発生しました。
  - **対策**: 外部リポジトリの clone / checkout コマンドに `GIT_LFS_SKIP_SMUDGE=1` や `git -c filter.lfs.required=false` を付与することで回避できることを実証・ドキュメント化しました。

### 軸 2: 証拠 JSON の抽出精度
- **多言語・モノレポのテスト探索**:
  - `pnpm/pnpm`（TypeScript + Rust の巨大モノレポ）において、`TEST_FILE_FIND_EXPR` に複数拡張子（`-name "*.test.ts" -o -name "*_test.rs" -o -name "test.rs"`）を指定することで、全サブパッケージを横断して 404 ファイル（3,714 テストケース）を漏れなく捕捉できました。
- **シンボリックリンクの認識**:
  - `CLAUDE.md -> AGENTS.md` のようなシンボリックリンク運用でも、指示書ファイルとして二重カウントされずに正常に認識されました。
- **AI 協働（L 項目）の計測精度**:
  - `cline/cline`（293 件 AI レビュー / 168 件 人間承認）、`pnpm/pnpm`（485 件 AI レビュー / 181 件 人間承認）など、大規模 OSS で実際に回っている「AI が一次レビューを行い、人間が最終判断する」共同監督（shared oversight）の実態が鮮明に定量化されました。

### 軸 3: 判定基準（criteria.md）の妥当性
- **単独メンテナの N/A 判定**:
  - `Wolfe-Jam/faf-cli`（`single_author: true`）において、A（知識継承）のレベル 4（他者オンボーディング）が正しく N/A になり、スコア上限が 3 に抑えられました。
- **リポジトリ種類ごとの N/A 判定**:
  - クライアント・CLI ツールでは、本番監視（G）やデータ管理（H）が適切に N/A 除外されました。
  - さらに UI を持たない純粋関数ライブラリ（`sindresorhus/is`）では、合成ユーザーリサーチ（M）も適切に N/A 除外され、不当な減点が防止されました。
- **従来型 CI/CD と AI 成熟度の峻別**:
  - 10,000 件以上のテストや数百回のデプロイ実績がある老舗リポジトリでも、AI によるテスト生成や AI リリース運用がなければ E・F を 0 に留めるガードが機能し、評価の健全性が保たれました。

### 軸 4: 推奨アクションの有用性
- **共通のボトルネックの浮き彫り**:
  - AI 先進的なリポジトリであっても、**C（ADR: 設計決定記録）**、**B（AI 向け要件定義）**、**N（ふりかえり）** の 3 項目が共通して 0 に留まっており、これらが AI-SDLC における共通の成長痛であることがわかりました。
- **機械的判定可能な受け入れ基準**:
  - `c.adr_count >= 1` や `b.issue_template_exists == true` など、証拠キーに基づいた客観的な改善基準が提示されました。
