# AI-SDLC 成熟度アセスメント

`/assessing-ai-sdlc-maturity` と明示的に指定されたときだけ動く（モデルが自発的に呼ぶことはない）。引数: 第 1 引数は対象リポジトリのパス（省略時はカレント）。`再評価 #<番号>` が付いていれば、その親 Issue のベースラインと同じ版のシートで再採点し、差分だけを報告する。

## 概要

DEFRA「AI-SDLC Maturity Assessment」の 7 段階尺度（−1〜5）と階層準拠採点法を、Gigacore「AI-Maturity-Model」の 6 軸に対応づけた **固定の判定基準シート**（`criteria.md` 0.0.1）で、リポジトリの一次証拠（git 履歴・ファイル・GitHub の Issue / PR / Actions）から採点する。GitHub の外で回っているプロセスは証拠として拾えず低く出るので、結果はチームで話し合うためのドラフトとして扱う。基準をセッションごとに作り直すと四半期再評価で比較できなくなるので、**シートは正本として同梱し、変更は版を上げて差分を残す**。

## 手順

1. **フレームワークの差分確認**（初回、または 3 か月以上空いたとき）
   `curl -sL https://raw.githubusercontent.com/DEFRA/ai-sdlc-maturity-assessment/main/{README.md,introduction/ai-sdlc-maturity-assessment-framework.md,implementation/scoring-implementation.md}` と `https://raw.githubusercontent.com/Gigacore/AI-Maturity-Model/main/README.md` を取得し、尺度・採点ルール・軸が `criteria.md` 冒頭の記載と変わっていないか見る。変わっていればシートの版を上げる。次元ページの Sample assessment questions は、シートに無い項目を追加するときだけ取得する。
2. **証拠収集スクリプトの解決と実行**
   対象リポジトリから証拠収集スクリプト（`collect-evidence.sh`）を解決し、実行して一次証拠 JSON を得る（すべて読み取り専用。`.env` には触れない、既定窓 90 日）。
   - **スクリプトの探索順序**:
     1. リポジトリの `AGENTS.md` または `CLAUDE.md` に記録されたポインタ（`P-SDLC-COLLECTOR` 等）
     2. 標準パス（`.agents/collect-evidence.sh` または `scripts/dev/collect-evidence.sh`）
   - **スクリプトが未存在の場合（初回実行時の自動スキャフォールド）**:
     1. エージェントが対象リポジトリの構成（主要言語、テストランナー・テストファイルパターン、CI/CDワークフロー、ADRディレクトリ、変更履歴ファイル、設計・運用ドキュメントのディレクトリ、ラベル体系）を自動探索（プロファイリング）する。
     2. ユーザーに配置先パスを確認する（デフォルト: `.agents/collect-evidence.sh`。ユーザーが設定で上書き可能）。
     3. 本スキルの `templates/collect-evidence.template.sh` を読み込み、検出したプロジェクト固有の値で設定ブロックの `{{...}}` をすべて置き換えて（該当が無い項目は空文字にするとスクリプト内の既定値が使われる）指定パスにスクリプトを生成し、実行権限（`chmod +x`）を付与する。
     4. 指定された配置先パスをプロジェクトの `AGENTS.md` または `CLAUDE.md` の運用ルール節に 1 行（例: `- **P-SDLC-COLLECTOR**: 証拠収集スクリプトは \`<指定パス>\` を使用する`）明文化・記録する。
   - **実行**: 解決したスクリプトを実行し、出力 JSON を得る。出力 JSON は親 Issue にコードブロックでコメントする。数値は JSON の `evidence.<key>.value` から転記し、暗算・推測で埋めない。
3. **採点** — `criteria.md` の全項目について、レベル −1/0 は「状態の該当」、1〜5 は「基準の充足」として判定し、**1 から連続して満たした最高レベル**をスコアにする（−1 該当なら −1、1 未達なら 0）。
   - レベル 3 以上の充足には **運用の証拠**（実行回数・日付・件数・ログ）が要る。ルール・スキル・ワークフローが「存在する」だけでは 2 止まり。ワークフローは `gh run list` の conclusion（`skipped` ばかりなら未運用）、設定ファイル（`.importlinter` 等）はそれを呼ぶ pre-commit / Taskfile / CI の行が要る。ドキュメントが「強制している」と書いていても、それは検証すべき主張であって証拠ではない。
   - 0 と 1 の境界: 0 の行は状態の説明で、1 の基準を満たせば 0 に該当していてもスコアは 1 以上。1 未達のときだけ 0。
   - 今回のアセスメント自身が生成した Issue・文書・コメントは根拠にしない（「洗い出した」を自作自演で満たさない）。
   - リポジトリ外（監視ダッシュボード、Notion 等）でしか確認できない項目は「未確認 = 未達」と明記して採点する。外部で行った活動でも、その出力（PR・ルール変更・change-log 行）がリポジトリ内にあれば内部証拠として使える。
   - 適用不能な項目は N/A にし、理由を書く（単独メンテナの「他者育成」など。`criteria.md` の N/A 注記に従う）。統合や削除はしない。
4. **集計** — 軸スコアは配下項目の **最小値**（中央値を括弧で併記）。全体は「全項目の中央値・平均」と「階層準拠（全項目が満たす最高レベル＝最小値）」を **両方** 出し、最小値を決めている項目名を書く。
5. **出力** — 順に: 結論（2 指標と一言）／KPI 数値／軸別サマリ／項目別（判定基準・証拠・次レベルへのギャップ）／推奨アクション（対象項目と「現在→到達見込み」）／再評価周期／評価の限界（GitHub の外で回っているため証拠が取れなかったプロセスを含める）。ページ（Artifact）か Markdown で出す。
6. **永続化** — ベースラインは GitHub の親 Issue に「スコア表・根拠数値・次回再評価日・限界」と `collect-evidence.sh` の出力 JSON を記録し、推奨アクションは 1 件ずつ Issue にする（背景の証拠・やること・受け入れ基準・昇格見込みを含める。**受け入れ基準は証拠キーで書く**。例: `c.adr_duplicates == 0`、`f.smoke_steps >= 3 かつ f.deploy_runs.<workflow>.success > 0`）。再評価はその親 Issue にコメントで追記し、**前回の JSON と diff を取り、値が変わったキーを先に列挙してから採点の変化を説明する**。変わった項目だけ表にする。同じ HEAD に対する 2 回目以降の採点は「校正」として扱い、親 Issue に差分項目と新しい根拠数値だけをコメントする（新しい親 Issue は作らない）。証拠 JSON はリポジトリ内には保存しない（親 Issue のコメント本文のコードブロックのみ）。

## クイックリファレンス

| 場面 | すること |
| --- | --- |
| 尺度・軸を決める | `criteria.md` をそのまま使う。作り直さない |
| 初回実行 | リポジトリ構成を自動プロファイリングし、テンプレートからプロジェクト固有の `collect-evidence.sh` を生成して `AGENTS.md` にパスを記録 |
| 数値の根拠 | プロジェクト固有の `collect-evidence.sh` の出力 JSON（`evidence.<key>.value`）。取得件数の上限（`--limit`/`-L`）は同じキーの `limit` フィールドに入っている |
| 改善 Issue の受け入れ基準 | 証拠キーで書く（例: `c.adr_duplicates == 0`）。アセスメントと改善 Issue を同じ語彙で計測する |
| AI 関与率 | `Co-Authored-By` 率は **下限値** と明記（トレーラー無しコミットの由来は判別不能） |
| 全体スコア | 中央値と階層準拠（最小値）を併記。平均だけで語らない |
| 推奨の優先順 | 最小値を決めている項目 → 次に低い項目 → 昇格が 1 手で済む項目 |
| 既存の評価と食い違った | 運用証拠（`gh run list` の結果等）を添えて差分表にする。証拠が強い方を採る |
| 再評価 | 四半期。優先項目は月次。同じ版のシートで、変わった項目だけ報告 |
| 証拠キーの意味 | `references/evidence-keys.md` |

## よくある間違い

| 間違い | 直し方 |
| --- | --- |
| DEFRA の次元ページを 1〜2 枚だけ読んで残りの基準を自作する | シートを使う。自作した基準は再評価で比較できない |
| リポジトリ固有の収集スクリプトを作らずにグローバルの固定スクリプトで無理やり採取する | 初回スキャフォールドでプロジェクトの技術スタック（言語・テスト・CI等）に適合したスクリプトを生成する |
| スコアが違う 2 次元を 1 行に統合する（例: AI リテラシー 3 + 価値計測 2 → 2） | 統合しない。低い方の原因が見えなくなる |
| スキルやワークフローの存在をレベル 3〜4 の証拠にする | 存在は 2 まで。3 以上は実行の痕跡（`gh run list` の成功件数・日付）を示す。`skipped` 50 件は未運用 |
| AGENTS.md や README の「〜で強制している」を証拠として転記する | 実際にそれを呼ぶ pre-commit / CI / Taskfile の行を grep する。無ければ 2 |
| 作業ツリーの未追跡ファイル等、成熟度と無関係な観察を軸に混ぜる | 「所見」節に分け、採点に入れない |
| 単純平均だけを総合スコアにする | 最小値の項目が運用リスクそのもの。併記する |
| 評価結果をチャットにだけ残す | 親 Issue に記録しないと次回の比較対象が消える |
| 出力を確定した評価として扱う | GitHub の外（口頭の合意、別ツールの記録）で回っているプロセスは低く出る。「評価の限界」に書き、チームで話し合うためのドラフトとして渡す |

版は SemVer。変更内容はリポジトリの `CHANGELOG.md` を参照。
