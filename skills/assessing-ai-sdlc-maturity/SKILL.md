# AI-SDLC 成熟度アセスメント

`/assessing-ai-sdlc-maturity` と明示的に指定されたときだけ動く（モデルが自発的に呼ぶことはない）。引数：第 1 引数は対象リポジトリのパス（省略時はカレント）。`再評価 #<番号>` が付いていれば、その親 Issue のベースラインと比較できる版のシートで再採点し、差分だけを報告する。

## 概要

DEFRA「AI-SDLC Maturity Assessment」の 7 段階尺度（−1〜5）と階層準拠採点法を、Gigacore「AI-Maturity-Model」の 6 軸に対応づけた **固定の判定基準シート**（`criteria.md`）で、リポジトリの一次証拠（git 履歴・ファイル・GitHub の Issue / PR / Actions）から採点する。GitHub の外で回っているプロセスは証拠として拾えず低く出るので、結果はチームで話し合うためのドラフトとして扱う。基準をセッションごとに作り直すと四半期ごとの再評価で比較できなくなるので、**シートは正本として同梱し、変更は版を上げて差分を残す**。

## 手順

1. **フレームワークの差分確認**（初回、または 3 か月以上空いたとき）
   `curl -sL https://raw.githubusercontent.com/DEFRA/ai-sdlc-maturity-assessment/main/{README.md,introduction/ai-sdlc-maturity-assessment-framework.md,implementation/scoring-implementation.md}` と `https://raw.githubusercontent.com/Gigacore/AI-Maturity-Model/main/README.md` を取得し、尺度・採点ルール・軸が `criteria.md` 冒頭の記載と変わっていないか見る。変わっていればシートの版を上げる。次元ページの Sample assessment questions は、シートに無い項目を追加するときだけ取得する。
2. **証拠収集スクリプトの解決と実行**
   対象リポジトリの証拠収集スクリプト（`collect-evidence.sh`）を見つけて実行し、一次証拠の JSON を得る。スクリプトはすべて読み取り専用で、`.env` には触れない。既定の集計期間（窓）は 90 日。
   - **スクリプトの探索順序**：
     1. エージェント向け指示書（`AGENTS.md` / `CLAUDE.md` / `GEMINI.md` / `.github/copilot-instructions.md` 等）や README に書かれた `collect-evidence.sh` のパス
     2. 標準パス（`scripts/ai-sdlc/collect-evidence.sh`、`scripts/collect-evidence.sh`、`.agents/collect-evidence.sh`）
   - **スクリプトが無い場合（初回実行時のスキャフォールド）**：
     1. 対象リポジトリの構成を調べる。対象は、主要言語、テストランナーとテストファイルの命名、pre-commit・タスクランナー・CI の定義、デプロイ用ワークフロー、ADR ディレクトリ、変更履歴ファイル、エージェント向けルールの変更履歴、設計・運用ドキュメントのディレクトリ、ラベル体系、AI エージェントのコミットの署名。
     2. ユーザーに配置先のパスを確認する（既定：`scripts/ai-sdlc/collect-evidence.sh`）。
     3. 本スキルの `templates/collect-evidence.template.sh` を読み込み、設定ブロックの `{{...}}` をすべて手順 1 で調べた値に置き換えてスクリプトを生成し、`chmod +x` する。該当が無い項目は空文字にすれば、スクリプト内の既定値が使われる。値の引用符の制約は設定ブロック冒頭のコメントに従う。ヘッダーの著作権・ライセンス表示（MIT）は消さない。
     4. 配置先のパスを、そのリポジトリがエージェント向けに使っている指示書（無ければ README）に 1 行記録する（例：`- AI-SDLC 成熟度アセスメントの証拠収集スクリプト: \`<指定パス>\``）。
   - **実行**：スクリプトを実行して出力 JSON を得る。数値は JSON の `evidence.<key>.value` から転記し、暗算や推測で埋めない。対象が Public リポジトリのとき、または JSON を公開の場所に投稿する予定があるときは、`--anonymize-authors` を付けて実行する（`header.authors_top5` と `l.pr_authors_window` の個人名が仮の名前になる）。Private リポジトリでも、名前を出してよいかユーザーに確かめる。
3. **採点** — `criteria.md` の全項目について、レベル −1/0 は「状態の該当」、1〜5 は「基準の充足」として判定し、**1 から連続して満たした最高レベル**をスコアにする（−1 該当なら −1、1 未達なら 0）。
   - レベル 3 以上の充足には **運用の証拠**（実行回数・日付・件数・ログ）が要る。ルール・スキル・ワークフローが「存在する」だけでは 2 止まり。ワークフローは `gh run list` の conclusion（`skipped` ばかりなら未運用）、検査の設定ファイル（依存方向の検査、カバレッジ下限等）はそれを呼ぶ pre-commit・タスクランナー・CI の行が要る。ドキュメントが「強制している」と書いていても、それは検証すべき主張であって証拠ではない。
   - 0 と 1 の境界：0 の行は状態の説明で、1 の基準を満たせば 0 に該当していてもスコアは 1 以上。1 未達のときだけ 0。
   - 今回のアセスメント自身が生成した Issue・文書・コメントは根拠にしない（「洗い出した」を自作自演で満たさない）。
   - リポジトリ外（監視ダッシュボード、チャット、ドキュメントツール等）でしか確認できない項目は「未確認 = 未達」と明記して採点する。外部で行った活動でも、その出力（PR・ルール変更・変更履歴の記載）がリポジトリ内にあれば内部証拠として使える。
   - 適用不能な項目は N/A にし、理由を書く（単独メンテナの「他者育成」など。`criteria.md` の N/A 注記に従う）。統合や削除はしない。
4. **集計** — 軸スコアは配下項目の **最小値**（中央値を括弧で併記）。全体は「全項目の中央値・平均」と「階層準拠（全項目が満たす最高レベル＝最小値）」を **両方** 出し、最小値を決めている項目名を書く。
5. **出力** — 順に：結論（2 指標と一言）／KPI 数値／軸別サマリ／項目別（判定基準・証拠・次レベルへのギャップ）／推奨アクション（対象項目と「現在→到達見込み」）／再評価周期／評価の限界（GitHub の外で回っているため証拠が取れなかったプロセスを含める）。Markdown で出す（エージェントが HTML ページ等を出せる環境ならそれでもよい）。
6. **記録** — GitHub への書き込み（Issue の作成・コメント）は、ユーザーの確認を取ってから行う。書き込む前に、投稿先のリポジトリ（Public か Private か）、作る Issue の件数とタイトル、コメントに載せる内容（証拠 JSON を含むか、個人名が伏せてあるか）を示す。ユーザーが書き込みを望まないときは、同じ内容を Markdown で出力して終える。
   - **ベースライン**：GitHub の親 Issue に、スコア表・根拠数値・次回再評価日・評価の限界と、`collect-evidence.sh` の出力 JSON を記録する。証拠 JSON はリポジトリ内には保存せず、親 Issue のコメントのコードブロックにだけ置く。
   - **推奨アクション**：1 件ずつ Issue にする。背景の証拠・やること・受け入れ基準・昇格見込みを含め、**受け入れ基準は証拠キーで書く**（例：`c.adr_duplicates == []`、`f.smoke_steps >= 3 かつ f.deploy_runs.<workflow>.success > 0`）。
   - **再評価**：親 Issue にコメントで追記する。まず前回の JSON と diff を取り、値が変わったキーを列挙してから、採点の変化を説明する。表には変わった項目だけを載せる。`header.skill_version` が前回と違うときは、収集方法の変更で値が動いたキーがないかをリポジトリの CHANGELOG（末尾のリンク）で確かめ、採点の変化とは分けて書く。
   - **校正**：同じ HEAD に対する 2 回目以降の採点は「校正」として扱う。新しい親 Issue は作らず、差分のあった項目と新しい根拠数値だけを親 Issue にコメントする。

## クイックリファレンス

| 場面 | すること |
| --- | --- |
| 尺度・軸を決める | `criteria.md` をそのまま使う。作り直さない |
| 初回実行 | リポジトリ構成を調べ、テンプレートからプロジェクト固有の `collect-evidence.sh` を生成して、指示書か README にパスを記録 |
| 数値の根拠 | プロジェクト固有の `collect-evidence.sh` の出力 JSON（`evidence.<key>.value`）。取得件数の上限（`--limit`/`-L`）は同じキーの `limit` フィールドに入っている |
| 改善 Issue の受け入れ基準 | 証拠キーで書く（例：`c.adr_duplicates == []`）。アセスメントと改善 Issue を同じ語彙で計測する |
| AI 関与率 | AI エージェントの `Co-authored-by` を持つコミットの割合は **下限値** と明記（トレーラー無しコミットの由来は判別不能） |
| 全体スコア | 中央値と階層準拠（最小値）を併記。平均だけで語らない |
| 推奨の優先順 | 最小値を決めている項目 → 次に低い項目 → 昇格が 1 手で済む項目 |
| 既存の評価と食い違った | 運用証拠（`gh run list` の結果等）を添えて差分表にする。証拠が強い方を採る |
| 再評価 | 四半期ごと。優先項目は月次。前回と major・minor が同じ版のシートで行い、変わった項目だけ報告する（patch だけの違いは比較できる） |
| 証拠キーの意味 | `references/evidence-keys.md` |

## よくある間違い

| 間違い | 直し方 |
| --- | --- |
| DEFRA の次元ページを 1〜2 枚だけ読んで残りの基準を自作する | シートを使う。自作した基準は再評価で比較できない |
| どのリポジトリにも同じ固定スクリプトを使って証拠を集める | 初回スキャフォールドで、そのリポジトリの技術スタック（言語・テスト・CI 等）に合わせたスクリプトを生成する |
| スコアが違う 2 次元を 1 行に統合する（例：AI リテラシー 3 + 価値計測 2 → 2） | 統合しない。低い方の原因が見えなくなる |
| スキルやワークフローの存在をレベル 3〜4 の証拠にする | 存在は 2 まで。3 以上は実行の痕跡（`gh run list` の成功件数・日付）を示す。`skipped` 50 件は未運用 |
| AGENTS.md や README の「〜で強制している」を証拠として転記する | 実際にそれを呼ぶ pre-commit・タスクランナー・CI の行を grep する。無ければ 2 |
| 作業ツリーの未追跡ファイル等、成熟度と無関係な観察を軸に混ぜる | 「所見」節に分け、採点に入れない |
| 単純平均だけを総合スコアにする | 最小値の項目が運用リスクそのもの。併記する |
| 評価結果をチャットにだけ残す | 親 Issue に記録しないと次回の比較対象が消える（記録するかどうかはユーザーに確認する） |
| 確認なしに Issue を作る・個人名入りの JSON を公開の Issue に貼る | 書き込む前に投稿先と内容を示して確認を取る。Public リポジトリでは `--anonymize-authors` を付けて収集する |
| 出力を確定した評価として扱う | GitHub の外（口頭の合意、別ツールの記録）で回っているプロセスは低く出る。「評価の限界」に書き、チームで話し合うためのドラフトとして渡す |
