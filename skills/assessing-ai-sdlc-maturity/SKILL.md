# AI-SDLC 成熟度アセスメント

固定の判定基準シート（`criteria.md`）を使い、リポジトリの一次証拠（git 履歴・追跡ファイル・GitHub の Issue / PR / Actions）から 16 項目 × 7 段階（−1〜5）で成熟度を採点する。GitHub 外のプロセスは証拠として拾えず低く出るため、結果はチーム議論用のドラフトとして扱う。

※ 本文中の相対パス（`criteria.md`・`references/`・`scripts/`・`templates/`）はすべて本スキルディレクトリを基準とする（非インストール利用時も同様）。

## 引数とモード

実行開始時に引数から対象とモードを確定する。

- **対象リポジトリ**：第 1 引数（省略時はカレントディレクトリ）。
- **再評価モード**：`再評価 #<番号>` または `再評価 <前回証拠 JSON パス>`（別名：`reassess`）指定時。手順 1・6 で `references/reassessment.md` を参照する。
- **書き込みなしモード**：`書き込みなし`（別名：`no-write`）指定時、または対象リポジトリに依頼範囲外変更禁止規約があるとき。対象リポジトリにも GitHub にも書き込まない（手順 2・6 の具体手順は `references/collector-setup.md#書き込みなしモードと外部リポジトリ取得`）。

## 手順

### 1. フレームワーク差分確認

- **発火条件**：初回実行、または前回確認日（ベースライン JSON の `header.framework_checked_at`）から 3 か月以上経過しているとき → `references/reassessment.md#フレームワーク差分確認` を読み実行する。
- **完了条件**：手順 2 に渡す `--framework-checked-at` の値（今回の確認日／前回確認日の引き継ぎ／未確認 `null`）が確定している。

### 2. 証拠収集スクリプトの解決と実行

対象リポジトリの `collect-evidence.sh`（読み取り専用・`.env` 非接触・既定窓 90 日・git 追跡ファイルのみ対象）を実行し、一次証拠 JSON を得る。数値はすべて `evidence.<key>.value` から転記し、暗算や推測で埋めない。

- **探索・実行準備**：実行前に既定ブランチとのずれ・未コミット変更を確認する（詳細：`references/collector-setup.md#評価対象コミットと実行準備`）。スクリプト探索順序は `references/collector-setup.md#収集スクリプトの探索順序`。
- **分岐ポインタ**：
  - スクリプトが無い → `references/collector-setup.md#初回スキャフォールド`
  - 既存収集器または既存 JSON を使う → `references/collector-setup.md#既存収集器の互換性検査と救済`（**旧版 JSON の `header.criteria_version` / `header.skill_version` は書き換えず保持し、採点基準と収集器の版をレポートで分けて明記する**）
  - 書き込みなしモード／外部 clone → `references/collector-setup.md#書き込みなしモードと外部リポジトリ取得`
- **実行と匿名化**：Public リポジトリまたは公開投稿予定時は `--anonymize-authors` を付けて実行する。Private リポジトリでも個人名掲載の可否をユーザーに確認する。
- **ヘッダー確認（必須）**：`collection_errors` が空でも、`header.evaluated_ref`・`header.last_commit_date`・`header.single_author`・`header.repository_input` を必ず確認する。改名・取得失敗・`gh` 不可・休眠・単独メンテナ別名に該当する場合は `references/collector-setup.md#ヘッダー確認と例外対応` と `references/evidence-keys.md`（出力形式・未取得・補完クエリ）に従って対処する。
- **完了条件**：`evidence.json` が生成され、`header.evaluated_ref` が評価対象コミットと一致し、ヘッダー確認および `collection_errors` への対処方針（再取得・補完・保留）が確定している。

### 3. 採点

採点前に `criteria.md` の共通注記と A〜P 全 16 項目を必読し、シートの基準のみで採点する。

- **階層準拠**：−1/0 は状態該当、1〜5 は基準充足で判定し、1 から連続して満たした最高レベルをスコアにする（−1 該当なら −1、1 未達なら 0）。
- **レベル 3 以上の運用証拠**：ルール・スキル・ワークフローの存在だけはレベル 2 止まり。3 以上には実行実績（`gh run list` の conclusion；`skipped` や `action_required` のみは未運用、検査設定は pre-commit / タスクランナー / CI の呼び出し行）が要る。デプロイ以外の CI も同様に確認する。Actions 実行結果が取れない場合の証拠の強さは **(1) `gh run list` の conclusion > (2) マージ済み PR の `status:success`/`status:failure` 件数（代替証拠である旨を評価の限界へ記載）> (3) 定義のみ（レベル 2 まで）**。
- **`null` と `0` の区別**：`value: null` のキーは「未取得」として扱い、0 にしない。別証拠で判定できなければスコアを保留し、評価の限界に書く。
- **質的条件と廃止済みゲート**：**M≥3・L≥4・O≥3** の手動確認は「出どころ・対象期間・判定」の 3 要素を「主な証拠」に明記する。廃止済みゲート・指標の過去実績だけで現在の運用レベルを上げない（詳細：`criteria.md`）。
- **自己生成物の除外**：今回のアセスメント自身が作成した Issue・文書・コメントは根拠にしない。
- **N/A と自動化・指標の扱い**：適用不能項目は `criteria.md` の N/A 注記に従い理由を書いて N/A にする（項目の統合・削除はしない）。リポジトリの種類（本番サービス／ライブラリ・Action・CLI／データ基盤）は構成（`action.yml`・パッケージ公開設定・デプロイワークフロー・データ取り込み処理等）から判断してレポートに書き、判断が付かなければユーザーに確かめる。AI 以外の自動化は所見に書く。AI 関与率は下限値と明記し、歴史の長いリポジトリでは窓内の `k.coauthored_ratio_window` を主に使う。既存評価と食い違った場合は運用証拠を添えて差分表にし、証拠が強い方を採る。
- **外部運用の確認**：外部で運用している申告があってもスコアは変えず、「外部運用」列に `申告あり` と出どころを書く。採点完了後、G・H・M・N・O・P のうち N/A でなく証拠未取得（スコア 0 以下または保留）の項目を一覧にしてユーザーへ **1 回にまとめて** 尋ねる（選択肢：外部運用している＋場所／運用していない／分からない）。「運用している」は `申告あり`、それ以外は `申告なし`、問わなかった項目と未回答は空欄とする。非対話実行（クラウド・CI 等）では省略し、評価の限界に「外部運用は未確認（問いかけ未実施）」と書く。
- **完了条件**：A〜P 全 16 項目にスコア・N/A・保留のいずれかが付与され、レベル 3 以上の全項目に運用証拠、M≥3・L≥4・O≥3 に 3 要素が揃い、外部運用確認（対話時は一括質問完了、非対話時は省略記載）を済ませている。

### 4. 集計と検算

`scripts/verify-assessment.sh --scores <scores.json> --evidence <evidence.json>` を実行し、集計値と証拠 JSON の整合性を検算する。

- 軸スコアは配下項目の最小値（中央値を括弧併記）、全体は「全項目の中央値・平均」と「階層準拠（全項目の最小値と決定項目名）」を併記する。N/A 項目は集計から除いて結論に併記し、最小値決定項目や全項目のうち外部運用 `申告あり` の一覧も結論に併記する。
- **保留項目の扱い**：現行の `verify-assessment.sh` は `--scores` に整数 `−1〜5` と `"N/A"` の全 16 項目を必須とするため、保留項目があるときは `0` や `"N/A"` へ変換せず `--evidence <evidence.json>` のみで証拠検査を実行する。スコア集計は確定済み項目のみで算出し、保留項目は未確定項目として結論と評価の限界に明記する。
- **完了条件**：(a) `verify-assessment.sh`（通常時は `--scores`＋`--evidence`、保留項目があるときは `--evidence` のみ）が終了コード 0 で完了し、(b) `evidence_checks` で検出された全指摘（未取得・上限到達・件数矛盾）について再取得・上限到達キーの下限扱い・所見および評価の限界への記載を完了している。

### 5. 出力

`templates/report.template.md` の見出しと表の列を変えずにレポートを作成する（Markdown、または環境が許せば HTML 等）。推奨アクションは「最小値を決めている項目 → 次に低い項目 → 1 手で昇格できる項目」の順で並べる。

- **完了条件**：テンプレートの全セクションが欠落なく埋まり、数値が `evidence.<key>.value` と一致し、評価の限界に必要な項目（外部プロセス・未取得/補完/近似キー・フレームワーク差分確認有無）が揃っている。

### 6. 記録

ベースラインの置き場所（GitHub 親 Issue またはファイル）をユーザーに選んでもらう。

- **書き込み前の承認（必須）**：GitHub へ書き込む（Issue 作成・コメント投稿）前に、投稿先リポジトリ（Public / Private）、作成する Issue の件数とタイトル、コメント内容（証拠 JSON の有無、個人名匿名化の有無）を示してユーザーの確認を得る。
- **ベースライン（親 Issue）**：スコア表・根拠数値・次回再評価日・評価の限界と、証拠 JSON（リポジトリ内には保存せず親 Issue コメントのコードブロックのみ）を記録する。
- **ベースライン（ファイル）**：証拠 JSON を `assessment-<評価日>.json`、レポートを `assessment-<評価日>.md` としてユーザー指定場所（書き込みなしモードは対象リポジトリ外）へ保存する。
- **推奨アクション**：1 件ずつ Issue にする（起票しない運用ではレポートに記載）。背景の証拠・作業内容・受け入れ基準・昇格見込みを含め、**受け入れ基準は証拠キーで書く**（例：`c.adr_duplicates == []`、`f.smoke_steps >= 3 かつ f.deploy_runs.<workflow>.success > 0`）。
- **再評価・校正**：`references/reassessment.md` の手順に従う。
- **完了条件**：ユーザー承認済みの記録先へベースライン（または再評価・校正差分）と推奨アクションが記録されている。
